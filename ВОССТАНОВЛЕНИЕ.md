# Восстановление и production-подготовка bible-bot

Этот runbook описывает текущую production-архитектуру. Исторические executable runtime-монолиты удалены и не являются rollback-механизмом.

## 1. Что нужно сохранить

Для восстановления нужны реальные данные и идентификаторы:

- `BOT_TOKEN` от BotFather;
- `ADMIN_USER_ID`;
- `MONGO_URL` существующего MongoDB Atlas, если нужно сохранить пользователей, статистику и durable state;
- `BOT_USERNAME`;
- при явно заданном webhook secret — `TELEGRAM_WEBHOOK_SECRET`.

Старую инфраструктуру можно изучать только ради поиска credentials/configuration history. Она не определяет текущий runtime.

## 2. Канонический запуск

Единственная команда запуска приложения:

```bash
python production_entrypoint.py
```

`production_entrypoint.py` сначала настраивает production logging, затем импортирует `telegram_production.main()`.

`telegram_production.py` — единственный Telegram composition root. Quiz runtime находится в `telegram_quiz_runtime_controller.py`; course, challenge, retry, report, PvP, broadcast, settings, admin и другие surfaces подключаются focused controllers. MongoDB остаётся durable authority для persisted state.

Не восстанавливай удалённые runtime-монолиты как альтернативный launcher. Это создаст второй handler graph/state authority и обойдёт текущие deployment/import-graph гарантии.

## 3. Локальная проверка

```bash
git clone <repo>
cd bible-bot
cp .env.example .env
# заполнить BOT_TOKEN, ADMIN_USER_ID, MONGO_URL и при необходимости BOT_USERNAME
pip install -r requirements-dev.txt
python -m compileall -q .
pytest -q
python production_entrypoint.py
```

Для локального polling оставь:

```text
TELEGRAM_TRANSPORT=polling
```

Проверки:

```text
GET http://localhost:8080/live              -> process liveness
GET http://localhost:8080/ready             -> Mongo readiness
GET http://localhost:8080/telegram/ready    -> Telegram transport readiness
GET http://localhost:8080/production/ready  -> Mongo + Telegram production readiness
GET http://localhost:8080/                  -> Mini App
```

В Telegram `/start` должен открыть актуальный production handler graph.

## 4. Render

`render.yaml` — deployment authority. Актуальный контракт:

```text
build: pip install -r requirements.txt
start: python production_entrypoint.py
health: /production/ready
instances: 1
transport: webhook
webhook max connections: 1
auto deploy: checksPass
```

Основные environment variables:

```text
BOT_TOKEN
ADMIN_USER_ID
MONGO_URL
BOT_USERNAME
APP_ENV=production
TELEGRAM_TRANSPORT=webhook
TELEGRAM_WEBHOOK_MAX_CONNECTIONS=1
TELEGRAM_INIT_DATA_MAX_AGE_SECONDS=86400
PTB_TIMEDELTA=1
WEB_THREADS=4
```

После deploy проверяй не только `/live`, а production gate:

```text
https://<service>/production/ready
```

`/production/ready` возвращает success только когда готова MongoDB и Telegram transport.

В `@BotFather` Menu Button должен указывать на HTTPS URL сервиса/Mini App.

## 5. Webhook и cold start

Render production использует webhook через Waitress. Telegram update приходит на:

```text
POST /telegram/webhook
```

При cold start временный non-2xx не должен превращаться в потерянный update: Telegram повторяет доставку. Webhook остаётся зарегистрированным при обычном shutdown/sleep.

Для read-only проверки webhook из авторизованной среды:

```bash
python scripts/check_telegram_webhook.py
```

Скрипт использует `getWebhookInfo`, не меняет webhook и не печатает токен.

## 6. Polling rollback

Если во время инцидента нужно изолировать именно webhook transport, меняется только:

```text
TELEGRAM_TRANSPORT=polling
```

После этого redeploy выполняется с тем же:

```bash
python production_entrypoint.py
```

Это транспортный rollback. Handler graph, canonical quiz runtime и Mongo authority остаются теми же. Не возвращай исторический launcher.

## 7. MongoDB

Если прежний Atlas доступен, используй прежний `MONGO_URL` — так сохраняются пользователи, ranking, Telegram quiz sessions, Mini App sessions, battles, reports, broadcasts и idempotency evidence.

Перед rollout выполни read-only preflights из [`docs/DEPLOYMENT_PREFLIGHTS.md`](docs/DEPLOYMENT_PREFLIGHTS.md). Они проверяют duplicate/open sessions, exact unique indexes, retention/TTL, result-receipt growth и Mongo topology.

Не удаляй result receipts, незавершённые session rows или recovery evidence ради «очистки» без отдельного reviewed migration plan.

## 8. Mini App auth

Production API принимает пользователя из подписанного `X-Telegram-Init-Data` и проверяет HMAC, `auth_date` и signed `user.id`.

Debug authentication разрешена только при одновременных:

```text
APP_ENV=development
ALLOW_DEBUG_AUTH=true
```

В production это запрещено.

## 9. Проверка перед merge/deploy

Code admission:

```bash
python -m compileall -q .
pytest -q
node --check miniapp/app.js
```

GitHub Actions дополнительно выполняет dependency/secret checks, Ruff, full pytest, Mini App JS tests, Docker build, built-image production import, Mongo-backed container E2E, Security Audit и CodeQL.

Перед production deploy используй:

```bash
python scripts/run_production_acceptance.py predeploy
```

После deploy — postdeploy acceptance с точным `EXPECTED_DEPLOY_SHA`, как описано в [`docs/PRODUCTION_ACCEPTANCE.md`](docs/PRODUCTION_ACCEPTANCE.md).

Секреты не вставляй в git, PR comments или диагностические логи.
