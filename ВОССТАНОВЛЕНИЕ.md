# Восстановление и production-подготовка bible-bot

Актуальная схема проекта не требует старого набора «worker + Flask dev server + случайный внешний будильник».

## 1. Что нужно сохранить из старой установки

Нужны только реальные данные и идентификаторы:

- `BOT_TOKEN` от BotFather;
- `ADMIN_USER_ID`;
- `MONGO_URL` старого MongoDB Atlas, если нужно сохранить пользователей/статистику;
- username бота (`BOT_USERNAME`).

Старый Render/UptimeRobot можно проверять только ради поиска прежних access credentials и MongoDB URL. Код приложения от них не зависит.

## 2. Локальная проверка

```bash
git clone <repo>
cd bible-bot
cp .env.example .env
# заполнить .env
pip install -r requirements-dev.txt
pytest -q
python bot.py
```

Проверки:

```text
GET http://localhost:8080/live   -> 200
GET http://localhost:8080/ready  -> 200 только при доступной MongoDB
GET http://localhost:8080/       -> Mini App
```

В Telegram `/start` должен показать основное меню.

## 3. Почему теперь запускается именно `python bot.py`

`bot.py` запускает python-telegram-bot polling. В самом начале он импортирует `keep_alive`, а тот:

1. загружает `.env`;
2. стартует Waitress в отдельном daemon thread;
3. отдаёт Mini App и API на `$PORT` через пакет `web_api/`.

Так один процесс обслуживает Telegram и HTTP. Отдельный `gunicorn keep_alive:app` больше не используется, потому что при таком запуске Telegram polling вообще не стартовал.

Сам `bot.py` сохранён byte-for-byte как в `main`. Для его старого `from intro import ...` добавлен только явный `intro.py`, который реэкспортирует `questions.intro` и не копирует данные.

## 4. Render

`render.yaml` уже настроен как один Web Service:

```text
build: pip install -r requirements.txt
start: python bot.py
health: /live
```

Environment:

```text
BOT_TOKEN
ADMIN_USER_ID
MONGO_URL
BOT_USERNAME
APP_ENV=production
TELEGRAM_INIT_DATA_MAX_AGE_SECONDS=86400
WEB_THREADS=4
```

После deploy:

```text
https://<service>/live
https://<service>/ready
https://<service>/
```

В `@BotFather` настрой **Menu Button** на `https://<service>/`. Это нативный вход в Mini App; дополнительная перепись большого legacy `bot.py` для inline-кнопки не нужна.

### Важно про бесплатный Render

Free Web Service может spin down после периода без входящих запросов. Polling бота — исходящий трафик и не превращает free instance в always-on хостинг. Для реального 24/7 режима нужен always-on instance/другой always-on host. `/live` предназначен для health checking, а не для обхода тарифа.

## 5. MongoDB

Если старый Atlas доступен — используй прежний `MONGO_URL`; так сохранятся пользователи, рейтинг, bot quiz sessions, battles и reports.

Mini App использует отдельную коллекцию `miniapp_sessions` с TTL. Она не мешает старым `quiz_sessions` бота. Временные поля Mini App используют ту же naive-UTC модель, что и существующий `database.py`, поэтому PyMongo не смешивает aware/naive datetime при чтении и подсчёте длительности.

Если создаёшь новый Atlas, ограничь Database Access отдельным пользователем приложения и не публикуй connection string. Network Access настраивай настолько узко, насколько позволяет выбранный хостинг.

## 6. Что исправлено в Mini App

Раньше клиент получал вопросы без `correct`, но JavaScript подставлял `correct: 0`, поэтому реальные ответы проверялись неправильно. Кроме того, `/api/submit` принимал готовый score от браузера.

Теперь:

1. `/api/quiz/start` создаёт серверную сессию и перемешивает варианты на сервере;
2. браузер получает только **текущий** `id/question/options`, будущие вопросы заранее не выдаются;
3. после ответа `/api/quiz/current` выдаёт следующий вопрос и только тогда запускается его серверный таймер;
4. `/api/quiz/answer` принимает `session_id + question_id + chosen`;
5. сервер проверяет ответ, таймер и порядок вопроса;
6. размер теста фиксирует сервер: 10 обычный / 20 Challenge; короткий «тест на один вопрос» API не разрешает;
7. score/streak/points/bonus считаются сервером;
8. только законченная и подтверждённо записанная в MongoDB сессия считается успешной;
9. delayed/replayed answer идемпотентно возвращает уже сохранённый результат и не может стать ответом на следующий вопрос;
10. новый тест помечает прежнюю активную Mini App-сессию пользователя как `abandoned`;
11. leaderboard с именами/username требует Telegram-аутентификацию.

## 7. Telegram auth

Production API принимает пользователя только из подписанного `X-Telegram-Init-Data` и проверяет:

- HMAC hash;
- `auth_date`;
- наличие подписанного `user.id`.

Старый fallback `?user_id=123` удалён.

Для локального API-теста есть явный debug header, но только при:

```text
APP_ENV=development
ALLOW_DEBUG_AUTH=true
```

## 8. Зависимости

`python-telegram-bot` установлен с extra `job-queue`, поэтому периодические задачи бота (очистка/GC/напоминания) снова доступны.

`gunicorn` удалён из runtime: HTTP внутри bot process обслуживает Waitress.

## 9. Проверка перед merge

```bash
python -m compileall -q .
pytest -q
node --check miniapp/app.js
```

GitHub Actions выполняет эти проверки автоматически. PR остаётся draft до реального smoke test с настоящими `BOT_TOKEN` и `MONGO_URL`; секреты в репозиторий и комментарии PR не вставляются.
